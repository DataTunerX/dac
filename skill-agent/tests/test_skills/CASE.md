# A → B → C，且 B 走 2 轮

用本目录三个 skill 跑跨 SG 协作时，目标拓扑如下。

| 角色 | Agent（建议名） | Skill | 本域能回答 | 本域没有 |
|------|-----------------|-------|------------|----------|
| A | `user-agent` | `user-query` | 姓名 → 用户ID | 订单、商品 |
| B | `order-agent` | `order-query` | 用户ID → 订单号、商品ID | 商品名称、标价、库存 |
| C | `product-agent` | `product-query` | 商品ID → 名称、标价、库存 | 用户、订单 |

Join key：`用户名 → 用户ID → 商品ID`。C 不能按姓名或用户ID查，所以必须先经过 B。

## 推荐问句

```
张三买过哪些商品？请给出商品名称和现在的官方标价。
```

张三在数据里是 `U001`，订单对应 `PROD-001` / `PROD-003` / `PROD-016`。

## 期望执行

1. **A 一轮**：本地 `grep 张三` 得到 `U001`，本域无法回答「买过什么/标价」。按 skill 规则只委派 B，query 带上 `U001` 以及仍缺的名称和标价。**不要**直接委派 C（没有商品ID时 C 查不了「张三」）。
2. **B 第 1 轮**：只有用户ID，按 skill 规则**只跑本地订单查询**，得到商品ID，不要在这一轮委派 C。评估：用户要名称和标价，本轮只有 ID → 不通过。
3. **B 第 2 轮**：上下文里已有 `PROD-001` 等，委派 C，把这些商品ID写进 query。
4. **C 一轮**：按商品ID返回名称和标价。

B 所在 agent 需要 `max_loops >= 2`。若 B 第一轮就把 product 写进同一 plan，会变成单轮内本地+委派，**不是**本 case 要的两轮。

## 为什么 skill 要这样写

- A 的 skill **点名**订单、**禁止**在没有商品ID时找商品 → 链路是 A→B，不是 A 同时呼 B 和 C。
- B 的 skill **诚实**（只有商品ID），并写明「还没有商品ID时不要委派商品查询」→ 压成两轮，而不是 chain planner 一轮三步。
- C 的 skill **只收商品ID** → 倒逼必须先跑 B。
